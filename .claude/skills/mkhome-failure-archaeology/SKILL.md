## 1. Mobile hamburger unreachable — the transform trap (settled)

**The owner-confirmed costliest failure in the site's history.** Two years of intermittent mobile-nav pain, ended June 2026.

**Symptom:** On mobile, the hamburger button (☰) was invisible/unreachable, making the whole site un-navigable on phones. Recurred in different forms from Nov 2024 to Jun 2026.

**Root cause (final, 2026):** `#menuToggle` lived *inside* `.sidebar`, which gets `transform: translateX(-100%)` on mobile. **A transformed ancestor becomes the containing block for `position: fixed` descendants** — so the "fixed" button was positioned relative to the off-screen sidebar and slid off-screen with it.

**The arc (evidence):**

| Date | Commit | What happened |
|------|--------|---------------|
| 2024-11-10 | `e0c78f2` "Mobile friendly version" | First mobile attempt: moved inline sidebar-loader from index.html into script.js, added active-class toggling, `stopPropagation` |
| 2024-11-10 | `abe277b`, `23bfc1b`, `8808217` (three "Fix mobile version" in 8 minutes) | Same-day CSS thrashing to make it work — classic sign of fighting a misunderstood root cause |
| 2024-12-26 | `c774b45` "Fix the hamburger" | Removed a *duplicate* hardcoded `#menuToggle` from index.html (duplicate ID: one in index.html, one in sidebar.html), retargeted CSS to `.navbar-toggler` |
| 2026-06-06 | `8b05870` (merged as PR #1, `01136cc`) | Real fix. Commit message verbatim: *"The #menuToggle button was inside .sidebar, which has CSS transform: translateX(-100%) on mobile. A transformed parent creates a new containing block for position:fixed children, so the button was rendered off-screen and unreachable."* |

**Resolution (`8b05870`):** script.js now `document.createElement`s `#menuToggle` and a `#sidebarBackdrop` overlay and appends them **directly to `<body>`**, outside the sidebar, so the sidebar's transform can never capture them. Backdrop tap closes the drawer (standard drawer pattern). sidebar.html lost its Bootstrap navbar/button markup entirely.

**Standing rule derived:** **Never put `position: fixed` (or `position: sticky`-critical) elements inside `.sidebar`** or any transformed/`filter`ed/`will-change: transform` ancestor. If a new fixed overlay is needed, create it on `<body>` from script.js like the hamburger.

Also note: the button now exists only at runtime — grepping HTML for `menuToggle` finds nothing on index/store; it is generated by `initializeSidebar()` in `/home/user/html_projects/script.js`.

## 2. Production cache staleness (settled core; cache-busting still open)

**Symptom (2025-11-30):** After deploying the Phase 1–3 redesign, production (`mkhome.byst.re`) kept showing the *old* purple-gradient statistics section while local showed the new white design. CSS pushed and pulled on the VPS, but invisible to visitors.

**Root cause:** Two layers. (a) Original nginx config sent **no cache headers** for static files; (b) **Cloudflare** sits in front and caches assets ~4+ hours by default when origin sends no headers. Documented contemporaneously in `.ai/transformation-checklist.md` § "🔴 PRODUCTION DEPLOYMENT ISSUE (November 30, 2025)".

**Evidence:**
- `d3b862c` "chore: attempt to fix caching problem" — added per-type cache blocks to `.deploy/mkhome` and the checklist post-mortem (with before/after screenshots `.ai/local.png` / `.ai/production.png`).
- `0ac08b4` "fix: nginx config" — follow-up 6 minutes later fixing a **truncated header line** introduced in the same file: the old `add_header Feature-Policy "...magneto>` (a shell-wrap artifact ending in `>` — invalid) was replaced with a proper `Permissions-Policy` header. Lesson inside a lesson: nginx snippets copied from terminal output can carry truncation artifacts; always `sudo nginx -t`.

**Final state (verified in `/home/user/html_projects/.deploy/mkhome` today):** css/js → `expires 1h`; images/fonts → `1w`; html → `no-cache, no-store, must-revalidate`. This IS the deployed policy.

**Still open / candidate:** Versioned cache-busting (`styles.css?v=timestamp` + long max-age) is only a **comment** in the nginx file ("For production, consider using versioning…") and in the checklist's "Future Recommendation". Not implemented anywhere — no `?v=` query strings exist in the HTML. If a CSS change must be visible instantly, the procedure remains: purge Cloudflare cache (Dashboard → Caching → Purge) and hard-refresh; otherwise wait ≤1h.

## 3. SEO validation round — external validators found 4 real defects (settled)

**Symptom (2026-03-07):** After shipping the SEO infrastructure (`1285d55`), running the pages through real external validators surfaced concrete failures: Google Rich Results rejected the store's structured data; LinkedIn previews were blurry and missing a date.

**Root causes and fixes — all in `0fc1ba1` "fix: address SEO validation feedback from Facebook, LinkedIn, Google":**

| Defect | Validator | Fix |
|--------|-----------|-----|
| JSON-LD `@type: Book` had no price → not eligible for rich results | Google Rich Results Test | Switched to `@type: Product` with `offers.price`/`priceCurrency` (`author` → `brand`); price/currency added to `store/products.json`; `scripts/build-store.py` generator updated to match |
| Blurry share preview | LinkedIn Post Inspector | Added `og:image:width`/`og:image:height` (1200/630) to all pages |
| Missing date on share card | LinkedIn | Added `article:published_time` to store.html |
| Fuzzy text in OG image | (visual) | `scripts/generate-og-image.py` renders at `SCALE = 2` then `Image.LANCZOS` downscale — verified still present at lines 14/84 |

**Lesson:** Do not trust "SEO added" until the **real external validators** pass. The exact validator list (Facebook Sharing Debugger, LinkedIn Post Inspector, Google Rich Results Test, Schema.org validator, Lighthouse, Search Console) is preserved in `/home/user/html_projects/doc/seo-validation.md` (added in `0860584`).

## 4. Diacritics stripped from products.json — ES/PL text was ASCII-flattened (settled)

**Symptom:** Spanish and Polish store content shipped without diacritics: "Tecnologia para Seniors: Una Guia Practica", "Technologia dla Seniorow", "poczatkujacych" — reading as sloppy/machine-generated to native speakers.

**Root cause:** The initial `store/products.json` (`560677f`, 2026-03-04) was authored with ASCII-flattened text — accented characters were simply never entered. Not an encoding corruption of correct text, but the effect is the same: non-English content silently degraded.

**Evidence:** `f2194d1` "fix: add proper diacritics to Spanish and Polish text in products.json" (same day as launch, 2026-03-04) — dozens of word-level corrections ("Guia"→"Guía", "Seniorow"→"Seniorów", "poczatkujacych"→"początkujących").

**Resolution & guardrails now in place (verified in `/home/user/html_projects/scripts/build-store.py`):**
- Line 25: reads products.json with `encoding="utf-8"`.
- Line 48: `json.dumps(schema, ensure_ascii=False, indent=2)` — JSON-LD keeps real UTF-8 characters instead of `\uXXXX` escapes.
- All reads/writes of store.html/sitemap.xml pass explicit `encoding="utf-8"`.

**Lesson:** When touching ES/PL content, eyeball for missing diacritics (á é í ó ú ñ ¿ ¡ / ą ć ę ł ń ó ś ź ż). Never add `ensure_ascii=True` or drop the explicit encodings in build-store.py.

## 5. Hidden directories were servable in production (settled — re-check on every nginx change)

**Symptom:** `.ai/`, `.cursor/`, `.github/` under the web root were directly fetchable, e.g. `https://mkhome.byst.re/.ai/tech-stack.md` — leaking internal docs, dev config, and CI workflows. The deploy model (git pull of the whole repo into nginx's `root`) makes every committed file servable by default.

**Root cause:** nginx serves everything in document root; dotfiles are not special.

**Evidence:** `/home/user/html_projects/.ai/deployment-security.md` documents the problem and both fix options; `c1d8763` ("chore: phase 3 transformation", 2025-11-30) added `.deploy/mkhome` to the repo already containing the deny rule.

**Resolution (verified in `.deploy/mkhome` line 12):**
```nginx
location ~ /\. { deny all; access_log off; log_not_found off; }
```
The deliberate choice was "keep internal docs in git, block them in nginx" (rejected alternative: gitignoring `.ai/`).

**Status:** settled, but **fragile** — any rewrite of the nginx config must preserve this block. Verification after any nginx change: `curl -I https://mkhome.byst.re/.ai/tech-stack.md` must return 403/404; `index.html` must still return 200.

## 6. The 2024→2026 transformation arc — what shipped vs. what stalled (OPEN debts)

**Context:** Nov 2025, a planned visual/structural overhaul driven by `.ai/transformation-plan.md` + `.ai/transformation-checklist.md` + `.ai/transformation-examples.md` (added in `8f4804d` "chore: transformation plan").

**Shipped:** `a0ce807` (phase 1: styles.css overhaul), `8053d24` + `aef4d45` (phase 2: index.html restructure, script.js animations), `c1d8763` (phase 3: polish + nginx config into repo). Immediately followed by incident #2 (cache staleness) on deploy day.

**Stalled — the checklist still has 63 unchecked vs 33 checked items.** The security-relevant ones were re-verified against the working tree today and are ALL still open:

| Open debt (checklist lines 9–13) | Verified 2026-07-05 |
|----------------------------------|---------------------|
| SRI hashes on CDN links (Bootstrap, Font Awesome, jQuery) | no `integrity=` attribute in any *.html |
| Content-Security-Policy meta tag | no CSP `<meta>` in any page (only the weak nginx CSP header: `object-src 'none'; frame-ancestors 'none'; base-uri 'self'` — no script-src) |
| Replace `innerHTML` with safer DOM methods | `innerHTML` still used in script.js (sidebar injection line 6, hamburger icon swaps), store.html:645 (product grid), qr_code_generator.html:34 |
| Remove jQuery / standardize on vanilla JS | portfolio.html, projects.html, utilities.html still load jQuery and use `.load()` for the sidebar (the loader split described in mkhome-architecture-contract) |
| `rel="noopener noreferrer"` on external links | partial: index.html has 4 uses; portfolio/utilities/projects.html have 12 external links total with zero `noopener` |

**Do not treat these as bugs to "discover"** — they are known, deliberate, deferred. If asked to harden the site, this checklist is the backlog. Coordinate with `mkhome-change-control` before tackling (SRI in particular can break the site if a CDN file changes).

## When NOT to use this skill

- **Live-site triage right now** (site down, current console errors): use `mkhome-debugging-playbook`; come back here only to check whether the symptom matches a past battle.
- **How the site is *supposed* to work** (loader split, styling contract): `mkhome-architecture-contract`.
- **Making a change** (process, review, deploy steps): `mkhome-change-control`, `mkhome-deploy-and-operate`.
- **Store content edits**: `mkhome-store-pipeline` — this skill only explains *why* the pipeline's guardrails exist.
- Brand-new features with no resemblance to anything above — nothing here will help; just don't violate the standing rules (no fixed elements in `.sidebar`, UTF-8 discipline, don't hand-edit generated blocks).
